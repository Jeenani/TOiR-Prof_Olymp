### 3. Технические требования к компонентам решения

#### 3.1. База данных (PostgreSQL / Postgres Pro)
* Модель приведена к **3НФ**, таблицы имеют первичные ключи (PK) и внешние ключи (FK) с `ON DELETE RESTRICT` (на оборудование со связанными заявками) и `ON DELETE CASCADE` (на списание материалов при удалении заявки).
* **Ограничения (CHECK/UNIQUE):** уникальность инвентарного номера, номера заявки (формат `Z-YYYY-XXXX`), email, телефона. Контроль хронологии дат (дата ввода в эксплуатацию $\le$ дата ввода в работу $\le$ текущая дата; даты заявки: создание $\le$ план. начало $<$ план. окончание).
* **Триггеры:**
  1. *Триггер №1:* Запрет изменения статуса оборудования с «выведено из эксплуатации» на любой другой.
  2. *Триггер №2:* Комплексная валидация дат при вставке и обновлении заявок.
* **Хранимые процедуры и функции:**
  1. *Функция №1:* Расчёт суммарного времени простоя конкретного оборудования за период (в часах).
  2. *Функция №2:* Расчёт следующей плановой даты ТО (на основе даты последнего выполненного ТО и нормативной периодичности из справочника видов ТО).
  3. *Процедура №3:* Формирование сводного отчёта по цеху за период (статусы оборудования, количество аварийных/плановых заявок, простои, топ-5 материалов по расходу).

#### 3.2. Серверная часть (REST API)
* Единый формат ответов: `{ "success": boolean, "data": ..., "message": "...", "error_code": "..." }`.
* Авторизация по JWT токенам (Access + Refresh) и разграничение прав (RBAC):
  * *Администратор* (полный доступ);
  * *Главный инженер / Руководитель* (сквозная аналитика, дашборды, отчеты);
  * *Инженер по ТОиР* (управление нормативами, графиком плановых ТО, аналитика);
  * *Мастер цеха* (оборудование и заявки только своего цеха, создание заявок, списание материалов);
  * *Бригадир / Член бригады* (заявки, назначенные на их бригаду, фиксация выполненных работ).
* Защита: Rate limiting (100 запр./мин), валидация входящих DTO, временные ссылки на скачивание отчетов (срок жизни — 15 секунд для тестирования экспертами).

#### 3.3. Настольное приложение (Desktop)
* Нативная разработка (C# Avalonia / WPF, JavaFX или Python PyQt/Qt6) без WebView. Работа строго через REST API (прямой доступ к БД запрещен!).
* **Особые фичи:**
  * Автоблокировка интерфейса при бездействии 15 секунд;
  * Toast-уведомления и локальное логирование ошибок;
  * Сохранение введенных данных при обрыве сети и автоотправка при восстановлении;
  * Цветовая индикация графиков ТО (просроченные / ближайшие);
  * Контроль занятости ремонтных бригад при назначении;
  * Экспорт отчетов в PDF и Excel.

#### 3.4. Веб-клиент (Web SPA)
* Реализация на современном фреймворке (Vue.js / React / Next.js) с адаптивностью от 1024×768 до 1920×1080.
* **Дашборд:** 6 карточек KPI с индикацией трендов, интерактивные круговые и столбчатые диаграммы, линейный график динамики простоев, блок топ-5 простоев, автообновление каждые 60 секунд.
* **Real-time:** поддержка WebSocket или Server-Sent Events (SSE) с индикатором статуса соединения и автопереподключением при обрыве.
* **Аналитика:** фильтрация по периодам, цехам, типам ремонтов; экспорт диаграмм и таблиц.

#### 3.5. Тестирование (Модуль В)
Разработка набора Unit-тестов (не менее 3 функциональных блоков):
1. Тестирование расчёта времени простоя (нормальные даты, некорректная хронология, граничные случаи, null).
2. Тестирование валидации заявок (обязательные поля, аварийная заявка без указания причины, неверные плановые сроки).
3. Тестирование расчёта стоимости списанных материалов (несколько позиций, пустой список, количество = 0, отрицательные числа).
